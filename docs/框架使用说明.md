# 建模线对比实验使用说明

比较 T1–T6 在同一批整桥建模任务上的差别。任务、技能快照、模型和评分器相同。变的是各框架自己的编排，以及该框架官方接口上的动作方式。工具不是同一套。

环境用 `uv` 安装，不要把 `.venv` 或 `.venvs` 提交进仓库。安装步骤见 [ENVIRONMENT.md](../ENVIRONMENT.md)。知识怎么挂、时限数字的出处，见 [知识等量审计.md](知识等量审计.md) 和 [建模任务线接入说明.md](建模任务线接入说明.md)。以本文的运行口径为准。

## 正式口径

当前对比只跑 `full`（整桥）。`gen` 和 `edit` 是另外两种任务形式，不放进这一轮。

| 项 | 口径 |
| --- | --- |
| 模型 | `deepseek-flash` |
| 思考强度 | `low` |
| 种子 | `0` |
| 技能 | `checkpoints/train-all/skills`。不要挂父仓库原始 `.agents/skills`，那里有测试模板 |
| 单题总时限 | 7800 秒 |
| 生成阶段 | 最多 6000 秒 |
| 生成后预留 | 1800 秒，给编译、PyOSIS 和源码评分 |
| 交卷后 | 不把编译或建模报错送回。正式评分只对最后一版做一次 |
| 续跑 | `--resume` 跳过同时有 `evaluation.json` 和 `manifest.json` 的格子 |

`scripts/run_dataset.py` 和 `scripts/run_campaign.py` 不写 `--model` 时，默认仍是过期的 `deepseek-v4.1-flash-expires-on-0910`，思考强度也不会发出。正式对比必须把下面两个参数写上。

先设父仓库和密钥：

```powershell
$env:OSIS_PARENT_REPO = "C:\path\to\osis-skill-enhance-main"
$env:OSIS_MODEL_API_KEY = "<key>"
$env:OSIS_MODEL_BASE_URL = "https://api.deepseek.com"
```

OSIS 求解器是本机单例，端口 18080。启动时带上安装目录，例如 `--install <OSIS 安装目录>`。已经在听 18080 时不要再开第二个。

## 怎么开跑

一条题，只改 `--architecture`：

```powershell
uv run python scripts/run_dataset.py `
  --architecture T2 `
  --bridge osis-bridge-cantilever-box `
  --form full `
  --index 1 `
  --seed 0 `
  --model deepseek-flash `
  --reasoning-effort low `
  --parent-repo $env:OSIS_PARENT_REPO
```

索引从 0 起。父仓库 `datasets/test/<bridge>/full.json` 决定每座桥有几题。六座桥是 `osis-bridge-cantilever-box`、`osis-bridge-conventional-box`、`osis-bridge-hollow-slab`、`osis-bridge-precast-small-box`、`osis-bridge-precast-t-girder`、`osis-bridge-rigid-frame-box`。

整表只跑整桥：

```powershell
uv run python scripts/run_campaign.py `
  --label formal-full `
  --forms full `
  --resume `
  --model deepseek-flash `
  --reasoning-effort low `
  --parent-repo $env:OSIS_PARENT_REPO `
  --jobs 3
```

`--auto-forms` 会按 `full → gen → edit` 接着跑，并且前一阶段没全部终态就拒绝进入下一阶段。当前对比不要加这个参数。

`--no-pyosis`、`--no-solve-gate` 只用于排查，不能和正式分数放在一起。

## 并行

T1–T5 的生成可以并行，求解和评分在仓库锁上排队。`--jobs` 默认 3，是同一条 campaign 里的并行度。网关在主机 CPU 大约超过 90% 时会返回 503，这时把 `--jobs` 降到 1。

手工分列跑时，T2–T5 各保持一题。T6 独占 OpenCode 和求解器，不要和 T1–T5 同时启动，也不要同时开两个 T6。不要和验算修复的正式求解一起占 18080。

结果在 `runs/<label>/`。汇总见 [实验数据后处理.md](实验数据后处理.md)。

## 六个架构

环境由 `uv run python scripts/setup_framework_envs.py` 创建。T1、T2 用 `.venvs/main`，T3–T5 用 `.venvs/t3`、`t4`、`t5`。T6 用父仓库 `.venv`。驱动按架构选解释器。

| 架构 | 环境 | 动作 | 技能怎么给 | 候选工程怎么写 |
| --- | --- | --- | --- | --- |
| T1 | `.venvs/main` | 一次 `/chat/completions`，没有工具循环 | 请求前写入提示词，约 10 万字符，是技能正文和可见模板的子集 | 解析回复里的 `### FILE:` 块 |
| T2 | `.venvs/main` | LangGraph `create_agent` | `list_skills`、`read_skill`、`read_skill_reference`、`list_reference_files`、`search_skill_cases` | `read_candidate_file`、`write_file`。没有运行工程的工具 |
| T3 | `.venvs/t3` | smolagents `CodeAgent`，`tools=[]` | 解释器放行 `json`、`pathlib`、`pyosis`，用 `pathlib` 读快照 | 用 `pathlib` 写入 `candidate_project/` |
| T4 | `.venvs/t4` | OpenHands 默认智能体 | `load_skills_from_dir`，先 `invoke_skill` | 官方 `terminal`、`file_editor`。另有 `task_tracker`。浏览器关闭 |
| T5 | `.venvs/t5` | CrewAI：研究员、工程师、审查员 | `Crew(skills=...)` 的 `load_skill`。`load_skill` 只返回 `SKILL.md`，同一次 `kickoff` 里用 `read_skill_resource` 读快照里的其余文件 | 官方 `FileReadTool` / `FileWriterTool` / `DirectoryReadTool`，限制在候选目录。`allow_delegation=True`。代码执行关闭 |
| T6 | 父仓库 `.venv` | OpenCode 一次会话。提示是 `帮我建桥:{需求}`，问题监视用 `first`，等到空闲，不再发第二条消息 | 快照拷进隔离工程的 `.agents/skills` | 会话自己的文件和命令工具。空闲后由运行器对当前 OSIS 工程求解 |

## 为什么各框架能力不同

技能文档是同一份快照。比较的是各框架自己的动作接口。实验不另做一套人人都能调用的「运行工程」工具。某个框架的官方接口里没有执行器，就不给它补一个。交卷后也不把报错送回。

- T1 没有工具循环。一次请求里塞进约 10 万字符的技能子集，这是单次生成本身的做法。
- T2 用的 LangGraph `create_agent` 不自带工具。调用方不传入工具，它就只能回文字。实验交给它的是读技能和写候选工程：`list_skills`、`read_skill`、`read_skill_reference`、`list_reference_files`、`search_skill_cases`、`read_candidate_file`、`write_file`。`search_skill_cases` 只搜这份快照，不接知识库。库本身没有运行工程的动作，所以不加。
- T3 用的 smolagents `CodeAgent` 动作就是 Python。`tools=[]`，模型写代码，解释器执行。它能做什么，由解释器的允许导入名单决定。详见下一节。
- T4 用 OpenHands 官方的 `invoke_skill`、`terminal`、`file_editor` 和 `task_tracker`。终端是它自己的执行器，可以在同一次运行里跑命令。
- T5 用 CrewAI 的 `load_skill`、委托和 File Writer，在同一次 `kickoff` 里写文件。CrewAI 1.15 的 `CodeInterpreterTool` 已废弃，`allow_code_execution=True` 不会注册任何工具，所以代码执行保持关闭。T5 在循环里跑不了 PyOSIS，这是它现在的官方接口。`read_skill_resource` 只补 `load_skill` 读不到的同一份快照文件，不是运行工具。
- T6 用 OpenCode 自己的文件和命令工具。会话空闲后，运行器用父仓库的 Python 对已经留在 OSIS 里的模型求解。这一步对齐父仓库的测试流程，不是加给 T2 或 T5 的工具。

## 为什么只给 T3 接 pyosis

T3 的动作是 Python 解释器。导入一个库，就是这个解释器的正常动作。

允许名单里原来只有 `json` 和 `pathlib`。`pyosis` 被挡在外面，是名单写窄了。`CodeAgent` 并不是没有解释器。所以把 `pyosis` 放进 `additional_authorized_imports`。`os`、`subprocess`、`shutil` 仍然不放行，避免解释器变成任意命令行。

父仓库的 `pyosis` 装在 Python 3.11 里，T3 的虚拟环境是 Python 3.13。把父仓库整个 `site-packages` 加进 T3 的 `sys.path`，NumPy 的二进制对不上，`openai` 也会导入失败。`pyosis` 本身是纯 Python，还依赖 pandas。适配器只把 `pyosis` 目录链接到 `.venvs/t3/pyosis-link`，pandas 装在 T3 自己的环境里。不要把 `pyosis` 装进 `.venvs/main`。

T2 和 T5 不接。它们的官方接口里没有这个解释器。再给一个运行工具，就变成所有框架共用的执行器。T4 已经有官方终端。T6 的求解发生在会话空闲之后，由父仓库的 Python 调用 `OSISEngine().solve()`，不在 T3 的进程里导入。

网关若把 T3 的动作包成 DSML，只在模型边界还原成 `<code>`，代码本身不改。

交卷后各框架只在自己的工具循环里改文件。正式评分：T1–T5 用 `main.py` 重建并求解；T6 不重建，求解进程是父仓库的 Python。求解失败把正式分记为 0。

单架构命令把 `T2` 换成 `T1`、`T3`、`T4`、`T5` 或 `T6`。T6 不要和别的架构并行。
