# 建模任务线接入说明

## v2 执行口径（当前正式版本）

建模线只需要记住一条链路：

```text
同一个任务 JSON + 同一份技能快照（工具按各框架自己的接口，不是同一套）
  → T1–T6 各自生成 candidate_project
  → T1–T5：common/pyosis_adapter.py 运行 prep/main.py，再求解
  → T6：会话空闲后对当前 OSIS 工程求解，不重建 main.py
  → PyOSIS 的 OSISEngine.model_summary() 导出真实模型状态
  ├─ common/cli_scorer.py 调用父仓库已有 model_conformance CLI
  │   └─ model_score.json（源码主评分）→ evaluation.json
  ├─ 同一次执行的 manager.all() 详细记录
  │   └─ runtime_measurements.json
  │       └─ canonical 参数 → 父仓库桥型评分规则
  │           └─ runtime_score.json/.md（运行态旁路逐项评分）
  └─ manifest.json 固化版本/哈希/限时
```

这不是“都用 OSIS 框架来生成代码”：T1–T5 仍按各自编排方式生成代码，T6 使用 OSIS 原生编排；只有建模执行器和评分器统一。正式实验不依赖 OpenCode 或 OSIS 图形界面，T6 通过无界面的独立 OpenCode 服务运行原生工作流，图形界面只用于调试。T6 可以按已挂载的 `AGENTS.md` 做正常 L0/L1/L2 局部验证，但正式结果仍由外层 `ExperimentRunner` 统一收集和评分；正式数据运行默认开启求解并要求收敛，诊断时可用 `--no-solve-gate`。

项目内的职责划分如下：

```text
baselines/t*_*/       框架接入层：读取同一技能包，只产出 candidate_project
common/skill_adapter  只读挂载 SKILL、references 和文档
common/pyosis_adapter 真实 PyOSIS 执行、状态探针和日志
common/cli_scorer     调用 osis-auto-testconformance CLI
common/runner         固定顺序、限时、工件和 manifest
```

当前实验只比较“建模流程”，不比较聊天界面。每个 T1–T6 适配器的唯一交付物是一个候选 OSIS 工程：

```text
candidate_project/
└─ py/
   ├─ 项目画像.md
   └─ prep/
      ├─ main.py
      ├─ _0_engine.py
      ├─ _1_control.py
      ├─ _2_property.py
      ├─ _3_material.py
      ├─ _4_section.py
      ├─ _5_node.py
      ├─ _6_element.py
      ├─ _7_boundary.py
      ├─ _8_loadcase.py
      ├─ _9_analysis.py
      └─ _10_stage.py
```

## 一次实验如何接通

1. 适配器读取 `tasks/*.json`，其中包含桥型、任务形式、难度和自然语言要求。
2. 适配器可以读取只读的 `--skills-dir`，但只能在自己的工作目录写代码。
3. 适配器把完整生成结果或模块修改结果写入一个临时 `candidate_project`。
4. `scripts/run_modeling.py` 将其复制到 `runs/.../candidate_project`，不再读取源目录。
5. 比较器检查标准文件是否齐全、Python 是否可编译。
6. 统一 PyOSISAdapter 负责真实建模和 `model_summary()` 状态探针，再由统一 `model_conformance` CLI 评分；没有启用 PyOSIS 或服务不可用时，`backend_status.json` 标记失败/`not_configured`，本次实验不能算完整成功。

## 两级任务限时器

任务采用“总任务时限 + 分任务时限”两级预算，二者都是所有架构共享的实验控制变量，不能由某个框架自行延长：

```text
总任务时限 total_timeout_s
├─ P0 需求解析/桥型识别
├─ P1 建模假设/单位/材料
├─ P2 截面/节点/单元/边界/荷载/阶段
├─ P3 代码执行与编译
├─ P4 PyOSIS 模型状态探针（可选求解 gate）
├─ P5 model_conformance CLI 评分和诊断（交卷后不再返修）
└─ P6 产物整理与报告
```

正式基线的总时限为 7800 秒，从任务下发给 Agent 前开始，到 P6 产物写入和验证结束为止。其中生成阶段最多使用 6000 秒，保留 1800 秒给编译、PyOSIS 和源码评分。该预算对 T1–T6 完全相同，包含：

- LLM 首次调用、后续调用、并行调用、子智能体和重试；
- 技能/文档读取、工具调用、文件写入和代码编译；
- OSIS 建模、求解、收敛检查和结果验证；
- 框架自身的排队、状态轮询和清理开销。

每个 P 阶段再有一个 `subtask_timeout_s` 硬上限。阶段实际可用时间取“该阶段剩余分任务预算”和“总任务截止时间的剩余时间”中的较小值；进入下一个阶段不能重新获得完整的总时限。正式基线使用下列总时限；分任务预算由任务 JSON 显式给出并对所有架构保持一致：

```yaml
total_timeout_s: 7800
subtask_timeout_s:
  P0: 300
  P1: 450
  P2: 1800
  P3: 450
  P4: 1200
  P5: 600
  P6: 120
```

如果一个阶段包含多个 Agent 子调用，则这些调用共享该阶段的预算；并行调用、重试和子智能体也从同一分任务预算中扣除。

每个阶段只能使用总预算的剩余时间，不能在进入下一个阶段时重新计时。建议在运行目录中记录以下字段：

```text
total_timeout_s       # 冻结的单任务总时限
subtask_timeout_s     # 各阶段/分任务硬上限
started_at
deadline_at
elapsed_s
timeout_stage         # P0-P6 或 agent / build / solve / validate / postprocess
subtask_id
subtask_started_at
subtask_deadline_at
subtask_elapsed_s
time_to_candidate_s
time_to_compile_s
time_to_model_s
time_to_score_s
```

任一分任务达到上限时，先停止该分任务及其子进程；若该分任务是关键阶段（P0–P5），本次任务直接判定失败，不得自动重新开启一个新的完整分任务预算。若实验协议明确该阶段可恢复，才允许在总任务剩余时间内进行限定次数重试。总任务达到上限时，无论当前处于哪个阶段，都必须停止整条流水线。

超时后应保留已经生成的文件用于诊断，并写入：

```json
{
  "status": "timeout",
  "failure_code": "task_timeout",
  "timeout_scope": "task | subtask",
  "timeout_stage": "P0-P6",
  "complete_success": false
}
```

CLI 评分可以继续对超时前生成的代码出分用于诊断，但 PyOSIS 执行和模型状态验证分记为 0；超时运行仍计入该架构的失败样本，不能删除或选择性重跑。任务限时器指墙钟时间，不等同于 OSIS 施工阶段中的天数或时间荷载参数。

## 现阶段可直接运行的命令

下面命令仅用于诊断已有候选模板的 T6 建模输入/输出链路（不作为框架对比结果）：

```powershell
python scripts/run_modeling.py `
  --skills-dir "<comparison-repo>\checkpoints\train-all\skills" `
  --task "tasks\dev\bridge_whole_l1.json" `
  --candidate-project "<candidate-project>" `
  --architecture T6 `
  --parent-repo "<path-to-osis-skill-enhance-main>" `
  --runs-dir "runs\diagnostic\modeling" `
  --seed 0 `
  --execute-pyosis
```

上面是诊断命令，候选工程来自原始模板，只用于检查执行器；正式框架对比应使用
`scripts/run_dataset.py`，让 T1–T6 自己生成候选工程。只做候选工程调试时去掉
`--execute-pyosis`。正式运行默认把求解作为通过条件，诊断时可用 `--no-solve-gate`。`pyosis`
默认从 `osis-skill-enhance-main/.venv` 选择；也可用 `--pyosis-python` 显式指定。

模板顶层直接是 `prep/` 也可以，比较器会自动转换成标准 `py/prep/`。

## T1–T5 的接入约定

各框架只需实现一个生成函数，接口语义如下：

```text
generate(task, skill_reader, workspace) -> workspace/candidate_project
```

其中：

- T1：把固定技能/文档包一次性放入提示词，生成一次完整工程；
- T2：ReAct 循环。LangGraph 不自带工具，由适配器把读技能和写候选工程的工具交给 `create_agent`。提示只给技能索引和可见模板名，不预载每个模板的文件路径，不提供完整性检查，也不接知识库；
- T3：`CodeAgent` 执行 Python，用放行的 `pathlib` 读技能快照并写候选文件。解释器可以导入 `pyosis`：只链接父仓库里的纯 Python 包，不把整个 3.11 虚拟环境放进 T3 的 3.13 路径；
- T4：OpenHands 用 `invoke_skill` 加载技能，用官方 `terminal` 和 `file_editor` 写候选工程；
- T5：CrewAI 在同一次 `kickoff` 里用 `load_skill`、委托工具和 `FileWriterTool` 读写候选工程；代码执行关闭，不再在 `kickoff` 结束后另开工程师任务；
- T6：OSIS 原生路由。会话空闲后由统一运行器对已在 OSIS 中的模型求解，不再用 `main.py` 重建。

框架不需要实现自己的评分器，也不应修改 `runs/` 中的结果。生成阶段不把 PyOSIS 绑定成各框架共用的运行工具。交卷后不再把编译或建模报错送回。T1–T5 只负责生成候选源码；T6 在隔离的原生 OSIS 项目中可以按 `AGENTS.md` 完成建模后的局部验证。
生成完成后由 `common.runner.ExperimentRunner` 统一评分。T1–T5 用 `main.py` 重建并求解；T6 用父仓库 Python 对当前 OSIS 工程求解。构造分来自父仓库的
`test_conformance.py`：

```python
runner.run(task, architecture_id="T2", seed=0,
           candidate_project=workspace / "candidate_project")
```

注意：`candidate_project/` 是框架唯一的源码交付目录；`osis_project/`（以及其中的
`secmesh/*.vtk`、日志等）是 PyOSIS 执行候选源码时产生的后端运行产物，不是 T1–T5
的文件输出，也不会被当作候选源码评分。若候选工程不存在、目录不完整或编译失败，
统一运行器会在 `backend_status.json` 写明 `status=not_run` 和原因，表示 PyOSIS
尚未被调用；只有候选通过布局和编译后，才会进入 PyOSIS 建模阶段。

## 执行后运行态参数评分（独立旁路）

源码评分和运行态评分是两条并行结果：

```text
model_score.json / model_score.md
  ← 已有 model_conformance CLI 读取 candidate_project 源码（当前正式主指标）

runtime_measurements.json
  ← PyOSIS 执行完成后，从实际 manager.all() 记录保存节点、单元、截面、材料、
     边界、工况、施工阶段、钢束和 element group 等运行态数据
  → common/runtime_measurements.py
  → 51 个 canonical 参数（例如 L、H_root/H_mid、截面厚度、材料等级、预应力配置）
  → 父仓库同一套桥型 SCORERS
  → runtime_score.json / runtime_score.md
```

每次运行由 `ExperimentRunner` 自动尝试生成运行态 sidecar。参数只能来自执行后
落盘的 `runtime_measurements.json`；无法从实际记录可靠抽取的字段保持 `None`，并
记录在 `runtime_score.json` 的 `missing_params`，不得从任务目标、标准答案或隐藏模板
补齐。运行态异常只会产生 `not_available`、`extraction_error` 或 `score_error` 状态，
不会阻塞源码评分，也不会覆盖 `model_score.json`、`reference_score.json` 或
`evaluation.json.quality_score`。因此当前论文主表仍看源码 CLI 分，运行态分用于后期
模型真实性审计、逐项分析和补充表格。

新运行不需要额外命令；运行器完成后即可在 run 目录看到这三个文件：

```text
runtime_measurements.json   # 原始运行态快照（可复算）
runtime_score.json          # 参数、缺失项、维度/评分项和总分
runtime_score.md            # 同一父评分器生成的可读报告
```

已有快照也可直接调用 `common.runtime_scorer.evaluate_runtime_snapshot()` 重算，
而不触碰源码评分文件。批量汇总时运行 `scripts/export_results_xlsx.py`，工作簿会
额外生成 `运行态对比` 和 `运行态逐项评分` 两个 sheet；没有运行态快照的记录只在
`运行明细` 中标记不可用，不会被伪造为零分。

## 如何解释结果

- `static_conformance.json`：代码结构和桥型规则的静态分数；
- `compile.json`：Python 语法检查；
- `backend_status.json` / `build_status.json`：PyOSIS 建模、可选求解和状态探针；
- `model_state.json`：由 `OSISEngine.model_summary()` 导出的实际模型摘要；
- `runtime_measurements.json`：从执行后 PyOSIS manager 记录生成的详细运行态快照；
- `model_score.json` / `model_score.md`：已有 `model_conformance` CLI 的机器可读/原始报告；
- `runtime_score.json` / `runtime_score.md`：运行态参数抽取及复用父仓库规则后的独立逐项评分；
- `evaluation.json`：综合分数。必须有编译、PyOSIS 实际模型状态、父仓库评分和产物完整性；正式运行还要求求解收敛，诊断模式可用 `--no-solve-gate` 放宽。

因此，T1–T5 与 T6 必须使用同一套 `candidate_project` 合同和同一套评价入口；是否打开 OpenCode 界面不属于实验变量，正式实验采用无界面调用并把会话/日志写入运行目录。
